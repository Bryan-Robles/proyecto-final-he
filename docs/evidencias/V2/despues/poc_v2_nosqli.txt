Evidencia V2 - NoSQL Injection (DESPUES, version mitigada)
Fecha: 2026-11-09
App: OWASP NodeGoat, mitigated/ en http://localhost:4001
Categoria: OWASP A05:2025 Injection

Comando (la clave demo se pasa por POC_PASS, no se publica):
  docker compose -f mitigated/docker-compose.yml up -d --build
  BASE=http://localhost:4001 POC_PASS=<clave_demo> python3 poc-scripts/v2_nosqli.py

Salida:
  [V2] Destino: http://localhost:4001  userId=1
  [V2] Payload threshold: "0' || '1'=='1"
  [V2] Linea base (threshold=0): 1 fila(s) -> ['Node Goat Admin']
  [V2] Con inyeccion:            HTTP 400, 0 fila(s) -> []
  [V2] Regresion (threshold=10): HTTP 200 (aceptado), 1 fila(s) propia(s)
  [V2] Inyeccion rechazada (HTTP 400); un threshold valido se acepta (HTTP 200).
  [V2] RESULTADO: MITIGADO - la inyeccion no altero el resultado
  EXIT_DESPUES=0

Verificacion de XSS (el fix no debe introducir un sink nuevo):
  GET /allocations/1?threshold=<script>alert(1)</script> (con sesion)
  -> HTTP 400 | script reflejado sin escapar: False

Interpretacion:
  Tras la mitigacion, 'threshold' se valida con la regex ^\d{1,2}$ (entero 0..99)
  y la consulta usa el operador nativo $gt (se elimino $where). El payload
  "0' || '1'=='1" no pasa la validacion: el error se marca y el handler de la ruta
  responde HTTP 400 (error del cliente) con un mensaje fijo ("Invalid threshold"),
  por lo que no se refleja la entrada (sin XSS). Un threshold valido (10) se acepta
  (HTTP 200): la funcionalidad legitima se mantiene. El numero de filas de la
  regresion depende del valor aleatorio de 'stocks' del seed; lo determinista es el
  codigo HTTP.
